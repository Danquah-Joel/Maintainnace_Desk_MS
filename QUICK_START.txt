🚀 GETTING STARTED (60 SECONDS)
===============================================================================

OPTION A: Open in Browser (Fastest)
────────────────────────────────────
1. Download all files to a folder
2. Right-click on index.html
3. Select "Open with" → Choose your browser (Chrome, Firefox, Edge, Safari)
4. That's it! You're live.

OPTION B: Run a Local Server (Better)
──────────────────────────────────────
If you have Python 3:
  $ cd facilities-desk
  $ python3 -m http.server 8000
  
Then visit: http://localhost:8000

If you have Node.js:
  $ npx http-server

📝 DEMO SCRIPT (Perfect for Tomorrow's Presentation)
===============================================================================

1. START AT INDEX.HTML
   - Shows the landing page with two big buttons
   - Explain: "One path for students, one for staff"

2. CLICK "FILE A REPORT"
   → This opens file-report.html
   - Walk through the form
   - Point out: Category, Urgency, Building, Room, Description
   - Note: Optional photo upload
   - Note: Anonymous reporting option
   - Fill it out and click Submit

3. LOOK AT SUBMISSION SUCCESS
   → Shows ticket ID (e.g., WO-0001)
   - Point out: "Every report gets an automatic ticket number"
   - Click "Manage Ticket" to see it on the board

4. GO BACK TO INDEX AND CLICK "MANAGEMENT"
   → Opens login.html
   - Click "Login as Admin" (demo login, no credentials needed)

5. SHOW THE ADMIN DASHBOARD (admin.html)
   → This is the facilities staff view
   - Explain the board layout (cards showing all tickets)
   - Show filters: by category, building, status, urgency
   - Click on a ticket to see details
   - Advance status: Open → Acknowledged → In Progress → Resolved
   - Add a resolution note, click "Mark resolved"

6. SHOW THE DASHBOARD TAB
   → Statistics at the top
   - Total tickets, pending, in progress, resolved
   - Charts showing issues by category and status
   - Point out: "This is the data your university didn't have before"

7. EXPLAIN THE ARCHITECTURE
   - Reference the architecture diagram in the documentation
   - This prototype: All in-browser, no backend needed
   - Production version: Would have a database, real login, notifications

❓ COMMON QUESTIONS GRADERS MIGHT ASK
===============================================================================

Q: "Why no database in the prototype?"
A: "Scope decision. The focus was workflow design and UX. Production version
   (documented in the roadmap) would upgrade to PostgreSQL + REST API backend."

Q: "Isn't localStorage limited?"
A: "For a campus, yes — real system would be server-backed. But for this
   prototype and small deployments, localStorage is perfect. ~5-10MB per
   domain is more than enough for thousands of tickets."

Q: "Why this particular problem?"
A: "It's common, invisible, and never gets built because it's not glamorous.
   Perfect for showing real-world problem-solving, not just coding skill."

Q: "What about authentication?"
A: "The login page demos the flow. Production would use university OAuth
   (SAML/CAS) or a proper password backend. Documented in production roadmap."

Q: "Can you add more features?"
A: "Absolutely. All customization is documented in README.md. The code is
   modular and easy to extend with photo galleries, email alerts, etc."
